## 1. 문제 정의

### 왜 텍스트가 아니라 음성인가

같은 "괜찮아요"도 말투에 따라 뜻이 정반대다. 텍스트 감정분석은 STT를 거치며 **말투를 버리고 통화 전문만 남긴다** — 정확도 이전에 프라이버시 문제이기도 하다.

근거로 삼은 공식 통계:

| 수치 | 출처 |
|---|---|
| 같은 결혼생활 만족도 — 남편 80.5% vs 아내 70.7% (9.8%p 차) | 통계청 「2024년 사회조사」 |
| 외로움 21.1% · "아무도 나를 잘 알지 못한다" 16.2% | 국가데이터처 「2024 한국의 사회지표」 |
| 직장 내 괴롭힘 **신고** 12,253건, 5년 만에 5.8배 | 고용노동부 제출자료(2025.2) ※ 신고 건수이지 발생 건수가 아님 |

> 조사 과정에서 흔히 인용되는 "이혼 사유 성격 차이 43.1%", "감정노동자 646만 명", "콜센터 통화의 1~3%만 모니터링"은 **출처 검증에서 탈락**시켰다. 각각 2018년 폐지된 통계, 2016년 언론 보도, 벤더 마케팅 블로그가 원출처였다.

### 왜 '분류기'가 아니라 '흐름'인가

처음엔 "음성 → 감정 7종 분류기"로 잡았다가 **9/21에 뒤집었다.**

- "wav 넣으면 슬픔 0.7" → *그래서 뭐?*
- "3분 통화에서 1분 2초에 확 틀어졌습니다. 클릭하면 그 구간 재생" → 쓸 수 있는 서비스

이 전환에는 데이터 근거가 있었다 (§2-3 대화 흐름 실측).

### 문제를 어떻게 정의했나

"감정을 분류한다"가 아니라 **"어디를 들어야 할지 알려준다"**로 정의했다. 이 정의 덕분에 이후의 모든 선택 — 3초 창, 신뢰도 보류, 구간 재생, 운영 액션 단위 출력 — 이 하나의 논리로 이어진다.

## 2. 데이터

### 2-1. 왜 AI-Hub였나 (5단 논리)

1. 원한 건 **일상 대화의 자연스러운 감정 흐름**
2. 개인 대화 녹음은 **동의·프라이버시** 때문에 수집 불가
3. 크롤링해도 감정 라벨이 없다 → 직접 달면 **43,991 × 평가자 5명 ≈ 22만 번의 판단**. 2인 팀의 규모가 아님
4. 그래서 **이미 5명이 라벨링을 끝낸** AI-Hub 감정 대화 음성 데이터셋(4·5차년도, 43,991클립 / 45시간) 선택
5. **그 투표가 오히려 무기가 됐다** → 아래 발견으로 이어짐

> 입력은 **비정형 데이터(음성 파형)** 하나다. CSV에 있던 발화문 텍스트·'상황' 컬럼 같은 정형 컬럼은 manifest 단계에서 전부 제외했다.

### 2-2. EDA에서 찾은 세 가지 함정

**① CSV의 `상황` 컬럼은 정답이 아니었다 — 일치율 68.1%**

`상황`은 성우에게 준 **연기 지시**였고, 평가자 5명이 실제로 느낀 감정(청취 다수결)과 68.1%만 일치했다.

- disgust로 연기한 것의 **48%만** 혐오로 들림, 16%는 분노로
- surprise로 연기한 것의 **38%는 그냥 중립**으로 들림

→ 라벨을 **평가자 5명 다수결(hard) + 투표 분포(soft)** 로 재정의.

> 이 데이터를 골랐기 때문에 이걸 찾을 수 있었다. 정답이 하나뿐인 데이터였다면 **라벨이 틀렸다는 사실조차 몰랐을 것**이다.

**② 화자가 111명뿐이고 상위 2명이 22%**

speaker_id가 없어 `(소스, 나이, 성별)` 조합으로 화자를 추정. 랜덤 split을 쓰면 같은 화자가 train/test 양쪽에 들어가 모델이 **목소리를 외운다.**

→ **화자 독립 분할** 강제 + split 단계에 누수 assert 추가.

**③ 클래스 불균형 13.6:1** (sadness 16,856 vs surprise 1,241)

→ 지표를 accuracy가 아닌 **UAR(macro recall)** 로. CB-Focal + 역빈도 균형 샘플러.

추가 관찰: 5명 전원 일치는 **31%뿐**, 3명 이하 합의가 **43%** — 사람끼리도 감정 판단이 갈린다. 그래서 투표 비율을 soft 라벨로 함께 학습했다.

### 2-3. 대화 흐름 실측 — `wav_id`가 ObjectId였다

EDA 때 "speaker_id 없음"으로 정리했지만 반쪽이었다. `wav_id` 24자리는 MongoDB **ObjectId**이고 앞 8자리에 **녹음 시각**이 들어 있다.

- 43,991건 전부 유효 · 시각 범위 2020-01-20 ~ 11-25
- 같은 프로세스 + 같은 화자 + 5분 이내로 묶어 **세션 9,400개** 복원
- 세션 안에서 연속 동일 시나리오 = **시나리오 블록 24,851개**

**측정 결과** (3발화 이상 블록 1,687개 · 발화 7,601건 · 연속 쌍 5,914개)

| 발견 | 수치 |
|---|---|
| 감정에는 관성이 있다 | 다음 발화도 같은 감정일 확률 **84.6%** (무작위 셔플 기대값 46.3% → 1.8배) |
| 전이는 비대칭이다 | 분노→슬픔 **21.1%** vs 슬픔→분노 **4.7%** (4.5배) |
| 감정은 붙잡아도 흘러간다 | 시나리오 1번째 발화 일치율 88.3% → 7번째 **66.0%** |

> **대칭이면 순서가 의미 없다. 비대칭이라는 건 흐름을 봐야 한다는 뜻이다.** → 서비스를 '흐름'으로 재정의한 근거.

이 수치가 말하지 않는 것도 함께 기록했다 — 한 시나리오의 발화가 전부 같은 화자라 **감정 전염은 이 데이터로 잴 수 없고**, 발화 간격 중앙값 44초라 실시간 대화가 아니며, 이건 모델 성능이 아니라 **사람 5명이 들은 결과**다.

### 2-4. 전처리와 분할 — 숫자를 셀 수 있게

```
43,991 (원본)
 → 39,188  라벨 필터: 동점·전원 불일치 4,803개 제외
 → 39,180  오디오 처리: 0.8초 미만 등 8개 제외
 → train 31,162 (79명) / val 3,178 (16명) / test 4,840 (16명)
```

- **버린 4,811개는 전부 이유를 셀 수 있다**
- 48kHz → 16kHz 리샘플, 피크 정규화, 앞뒤 무음 제거(30dB), 캐시 1회 생성 후 모든 실험이 공유
- 학습과 **동일한 정규화를 서비스에서도** 사용: `(y − mean) / max|y| × 0.891`
- 길이 평균 4.9초 · 중앙값 4.3초 · 상한 8초(88.6% 포함)

### 2-5. SKT 감정 음성 코퍼스 (추가 확보, 100GB)

| 구분 | 내용 |
|---|---|
| large | 화자 **8명** × 약 19,000발화 ≈ 15만 발화, 감정 16종, 48kHz, 67.3GB |
| small | 화자 약 500명, **라벨 없음** (의사라벨링 대상) |

**냉정하게 본 한계 3가지**: ① 화자가 8명뿐 — 진짜 병목인 화자 다양성은 해결 안 됨 ② 청취 검증이 없음 ③ 16종 중 46%가 7감정에 매핑 불가.

**결정적 발견** — 화자 M0001에서 `NEUTRAL` 라벨 수와 `#지문`(나레이션) 발화 수가 **각각 4,797로 정확히 일치**했다. SKT의 중립은 대화 중립이 아니라 **나레이션 낭독**이다.

**혼합 설계**: 151,680 → 매핑 가능 119,411(78.7%) → 전처리 115,062 → **4만 발화 균형 추출** → AI-Hub train 31,162 + SKT 40,000 = **71,162**. 불균형 16.5:1 → 약 9:1. SKT는 **학습에만** 쓰고 판정은 AI-Hub test로만 했다.

## 3. 모델

### 3-1. 설계 결정과 그 이유

| 결정 | 이유 | 검토한 대안 |
|---|---|---|
| 백본 **WavLM-base-plus** | 45시간은 밑바닥 학습에 부족. SSL 사전학습이 운율·음색 표현을 이미 보유 | MFCC+LSTM(약함), large 계열(8GB 초과) |
| CNN 특징 인코더 동결 | MFCC 자리를 학습된 필터로 대체하되 고정 | 전체 학습(VRAM·과적합) |
| **레이어 가중합** | 감정 정보가 어느 층에 있는지 모델이 직접 고르게 | 마지막 층만 사용 |
| **Attentive Statistics Pooling** | 감정은 어미 억양·강세 등 특정 구간에 몰림 | mean pooling |
| soft label KL (w=0.5) | 5명 중 3명만 동의한 샘플에 100% 확신을 강요하지 않기 위해 | hard label만 |
| bf16 + gradient checkpointing | 8GB에 9,497만 파라미터를 올리기 위해 | fp16(스케일러 이슈), fp32(OOM) |
| **서빙은 단일 모델** | 앙상블이 내부 test에선 +0.011이지만 **외부 검증에선 이득 없음** | 앙상블 서빙 |
| SKT는 **혼합 학습만** | 화자 8명 단독 학습 시 파국적 망각 | SKT 단독 이어학습 |

**구조**
```
16kHz 파형(최대 8초)
 → CNN 인코더(동결·20ms) → 트랜스포머 12층(WavLM)
 → 13개 층 출력의 가중합 → Attentive Statistics Pooling
 → 헤드 256 → 7감정 확률
```
총 **9,497만 파라미터** · batch 32 · 10 epoch · CB-Focal + soft KL · bf16 · RTX 4090

### 3-2. 실험 비교

**A. 백본·접근 비교** (고신뢰 서브셋 n_votes≥4 · 화자 독립 test **n=3,329**)

| 접근 | UAR | WAR | macro F1 | 학습 시간 |
|---|---|---|---|---|
| 랜덤 (7클래스) | 0.143 | — | — | — |
| emotion2vec+ large 프리즈 + 헤드 | 0.287 | 0.340 | 0.203 | 수 분 |
| emotion2vec+ large 제로샷 | 0.326 | 0.360 | — | 0 |
| emotion2vec_base 프리즈 + 헤드 | 0.573 | 0.771 | 0.605 | 수 분 |
| **WavLM-base-plus 파인튜닝 (기준 모델)** | **0.734** | **0.817** | **0.683** | 2~3시간 |
| 앙상블 (WavLM 0.70 / e2v 0.30) | 0.745 | 0.826 | 0.703 | — |

**B. 전체 데이터 학습** (전체 test **n=4,840** — A와 시험지가 달라 직접 비교 불가)

| 모델 | UAR | WAR | macro F1 |
|---|---|---|---|
| full_1731 (AI-Hub 전체) | 0.6754 | 0.7145 | 0.6857 |
| mix40k (+ SKT 4만 혼합) | 0.6626 | 0.7302 | 0.6985 |
| **mix40k + 로짓 보정 τ=0.6 (서빙 모델)** | **0.6945** | **0.7211** | — |

### 3-3. 핵심 발견 3가지

**① "제일 센 모델"이 제일 좋은 특징은 아니다**

`emotion2vec_plus_large`(4만 시간 다국어 감정 데이터 학습)를 기본값으로 썼는데 UAR 0.287 — **제로샷(0.326)보다도 낮았다.** 이미 자체 9클래스 분류기까지 파인튜닝된 모델이라 임베딩 전이가 안 된 것. SSL 원본 `emotion2vec_base`로 바꾸자 **0.573, 2배**.
→ 교훈: **파인튜닝된 분류기의 임베딩 ≠ 좋은 전이 특징.** 진단은 선형 프로브로 "특징이 나쁜가 헤드가 나쁜가"를 분리.

**② SKT 혼합은 UAR을 올리지 못했다 — 그런데 보정과 만나니 달라졌다**

SKT 4만 혼합 후 모델이 "확실할 때만 희소 감정을 고르는" 쪽으로 이동했다 (놀람 정밀도 .602→**.810**, 공포 .723→**.816**, 재현율은 하락). 주 지표 UAR은 −0.013.

그런데 **로짓 보정**(`logits − τ·log(학습 분포)`)을 적용하자:

| | τ (val에서 선택) | test UAR | test WAR |
|---|---|---|---|
| full_1731 + 보정 | 0.8 | 0.6967 | **0.6671** ↓ |
| **mix40k + 보정** | **0.6** | **0.6945** | **0.7211** |

보정 후 UAR은 동급(차이 0.002 = 오차)인데 **WAR이 갈렸다.** 기존 모델은 보정하면 슬픔 재현율이 .79→.64로 무너지지만, SKT 혼합 모델은 0.721을 지켰다.
→ **SKT가 만든 판별력 이득이 쏠림에 가려져 있다가 보정으로 드러났다.** 재학습 없이 UAR +0.03.
→ τ는 **val에서만 선택하고 test에는 한 번만 적용**했다. test로 고르면 반칙이기 때문.

**③ 중립은 감정이 아니라 잔여 범주였다**

| 채점 조건 | UAR | ACC | n |
|---|---|---|---|
| 지금 7감정 | 0.6945 | 0.7211 | 4,840 |
| 중립 라벨 제외·중립 예측은 오답 (공평) | 0.7041 | 0.7384 | 4,010 |
| 중립 선택지 자체 제거 | 0.7533 | 0.7968 | 4,010 |

공평 비교에서 **+0.010뿐**. 0.7533은 시험이 쉬워진 효과이지 개선이 아니다.
사람 라벨도 같은 말을 했다 — 중립 샘플은 n_votes 3.27(타 감정 4.08), entropy 0.754(0.403). **사람도 중립에서 덜 합의한다.**

보류 방식 비교: 중립=보류 → 커버리지 80.7% / 정확도 75.8% vs **신뢰도 0.70 보류 → 커버리지 50.3% / 정확도 90.1%**.

→ **결론: 중립 클래스는 유지, 판단 보류는 신뢰도 임계값으로만.** UI 표기는 "중립" 대신 "뚜렷한 감정 신호 없음".
→ 후속 가설(SKT 나레이션 중립 제외)은 **실험으로 기각**. 중립이 13,902→4,769로 줄자 역빈도 샘플러가 남은 중립을 3배 더 자주 뽑아 중립을 남발(정밀도 .573→**.462**). SKT 나레이션 중립이 오히려 평형추였다.

### 3-4. 학습 과정 기록 — TensorBoard로 찾아 고친 것

점수만이 아니라 **train loss · val 지표 · 레이어 가중치 13개 · 임계값 14단계**를 매 에폭 기록했다.

| 본 것 | 수치 | 고친 것 |
|---|---|---|
| train loss는 계속 내려가는데 **val UAR은 2에폭부터 평평** | loss 1.162→0.282 / val 0.466→0.617(ep5)→0.603(ep6) | ep5를 best로 저장하고 **조기 종료** |
| 13개 **레이어 가중치**가 균등에서 **상위층으로 쏠림** | 학습 전 0.067~0.087 → L09~L11 **0.153~0.158** | 레이어 가중합 구조 유지 확정 |
| 임계값 14단계 커버리지/정확도 곡선 | 0.70에서 커버리지 72.3% / 정확도 92.0% | **임계값 0.70 채택 (감이 아님)** |

이어학습(mix40k) 곡선에서는 **ep0에 0.5537로 떨어졌다가 ep5에 0.6190으로 회복**(출발점 0.6174) — 망각 후 회복 패턴을 확인하고 ep8에 early stop 했다.

터진 실험도 기록에 남아 있다 — xlsr 한국어 백본은 1스텝, 초기 WavLM은 10스텝에서 멈춘 기록이 그대로 있어 **무엇이 언제 죽었는지 추적할 수 있었다.**

## 4. 검증

### 화자 누수 검증 (통과)

- val UAR 0.7408 → test UAR 0.7342 — **처음 보는 화자에서 유지**
- 화자별 정확도 하위 5: 0.634 / 0.717 / 0.734 / 0.742 / 0.763 (붕괴 없음)
- 성별: female 0.808 / male 0.849 (남성 데이터가 27%뿐인데 더 높음)

> 이어학습 실험 중 **누수를 직접 발견하기도 했다.** 출발점 체크포인트를 바꿨더니 UAR이 0.7145로 튀어 의심 → 추적하니 test 화자 16명 중 11명이 그 체크포인트의 train 화자였고, test 4,840개 중 1,494개가 이미 학습한 파일이었다. 원인은 `min_votes`가 달라지면 화자 정렬 순서가 바뀌어 split 자체가 달라지는 것. **체크포인트는 split과 한 쌍이다.**

### 외부 검증 — 학습에 없던 목소리

| 채점 단위 | 정확도 |
|---|---|
| 7감정 그대로 | 50% |
| 운영 액션 4묶음(에스컬레이션/케어/관찰/정상) | 90% |
| 긍정·부정 2분류 | 100% |

세부 감정은 틀려도 **좋고 나쁨의 방향은 한 번도 틀리지 않았다.**
더 중요한 발견: WavLM과 emotion2vec이 **같은 구간에서 같은 실수**(중립→기쁨)를 했다. 서로 다른 두 모델이 같이 틀렸다면 모델 결함이 아니라 **두 데이터가 '중립'을 다르게 정의**한 것이다. → 서비스 출력을 7감정이 아니라 운영 액션 단위로 설계한 근거.
한계: 표본 10개 안팎, 합성 음성이라 실제보다 깨끗하다.

### 신뢰도 보정 — 서빙 임계값의 근거

| 임계값 | 커버리지 | 정확도 |
|---|---|---|
| ≥0.6 | 83.1% | 88.4% |
| **≥0.7** | **72.3%** | **92.0%** |
| ≥0.8 | 59.9% | 95.2% |
| ≥0.9 | 41.4% | 98.1% |

→ **0.70 채택.** 서비스 관점 지표는 에스컬레이션 탐지(분노+혐오 vs 나머지) F1 **0.837**, 3클래스 축약(부정/중립/긍정) 정확도 **91.4%**.

### 온디바이스 경량화 실측

| 항목 | 값 |
|---|---|
| 파라미터 | 9,497만 |
| fp32 체크포인트 | 약 380MB |
| **int8 동적 양자화** | **197MB** |
| RTF | **0.057** — 3.7초 오디오를 0.21초에 처리 |

양자화 중 `TypeError: expected Tensor ... but got method` 로 터졌다. WavLM 어텐션이 `q_proj.bias`를 **속성으로 직접 읽는데** 양자화된 Linear는 `bias`가 메서드가 된다. → 이름에 `.attention.`이 없는 Linear만 양자화(73개 중 25개). 그래도 197MB, 정확도 손실은 미미.

## 5. 서비스 구현

### 구조

```
브라우저 → nginx(web) ─/api/→ FastAPI(api) → Supabase (Storage + Postgres)
                                                  ↑ 대기열에서 집어감
                                            worker (WavLM 추론)
```

컨테이너 3개(**api · worker · web**)가 `docker compose up` 한 번에 기동한다.

**처리 흐름 ①~⑦**

1. 브라우저에서 업로드 (형식·100MB 검사)
2. 서버 전용 secret 키로 Supabase 접근 — **RLS 전면 차단**이라 브라우저가 DB를 직접 읽는 경로는 없다
3. 원본은 **비공개 버킷**에, 작업은 `analyses`에 `status=queued`로 등록 → **id만 즉시 반환**
4. 별도 큐 서버 없이 **DB의 상태 컬럼이 곧 큐** — 컨테이너가 죽어도 큐가 남아 재시작하면 이어서 처리
5. 워커가 **2초마다** queued를 집어감(claim) — 두 워커가 같은 작업을 집지 않아 `--scale worker=N`으로 안전하게 확장
6. 16kHz 변환 → 3초 창/1.5초 간격 → WavLM 추론 → 지역·현장 규칙 + 임계값 0.70 → `segments` 저장 후 `done`
7. 화면이 상태를 조회(결과 2초 · 대시보드 10초)해 타임라인 렌더, 구간 클릭 시 **1시간 서명 URL**로 그 지점부터 재생

**모델 배포**: 학습(GPU 서버)과 서비스는 완전히 분리돼 있다. `best.pt`를 Storage에 올리면 워커가 기동할 때 한 번 읽어 메모리에 올린다. **서비스 코드를 건드리지 않고 모델만 교체**할 수 있다.

### 실측

| 항목 | 값 |
|---|---|
| 69초 음성 | 45구간 · **추론 36.8초** / 전체 54.6초 (CPU, RTF 0.53) |
| 3분 통화 환산 | CPU 약 90~100초 (GPU 기준 RTF 0.057) |
| 저장 | `analyses`(통화+요약) / `segments`(3초 구간) / `feedback`(오분류 신고) |

### 화면

- **감정 흐름 타임라인** — 긍부정 곡선 / 각성도 / 7감정 레인 전환, 3초 구간 클릭 시 확률 상세
- **판단 보류** — 신뢰도 임계값 미만 구간은 비워둠 (단정하지 않음)
- **음성 재생 동기화** — 그래프를 누르면 그 지점부터 재생, 재생 중 우측 패널이 따라감
- **현장 선택** — 상담센터 / 교육 / 돌봄. 모델은 하나, 해석 규칙(임계값·문구·알림)만 교체
- **지역(사투리) 보정** — 지역 선택 시 그 지역 말투만큼 확률을 눌러줌, 보정 전/후 비교 토글
- **대시보드** — 일별 감정 분포·지역 분포·확인 필요 통화·오분류 신고 누적

### 시스템 상태 모니터링 (발표 피드백 반영)

"도커와 모델이 실제로 돌고 있는지 화면에서 확인되면 좋겠다"는 피드백을 받아 추가했다.

**설계** — api와 worker가 공유하는 볼륨을 이용해 DB 마이그레이션 없이 해결:
1. 워커가 2초마다 `worker_hb.json`에 심박을 쓴다 (상태 / 처리·실패 건수 / 모델 로드 여부 / 디바이스)
2. api가 `/system`에서 그 파일을 읽어 **15초 넘으면 죽은 것**으로 판정
3. 여기에 api 가동시간, Supabase 왕복 지연, 큐 상태(queued/running/done/failed)를 합쳐 반환

**화면** — 대시보드 상단 5칸이 5초마다 갱신: api 컨테이너 / worker 컨테이너(심박 N초 전) / 모델(버전·로드 여부·디바이스) / Supabase(지연 ms) / 작업 큐. 파일을 올리면 worker 칸이 **'대기 중' → '분석 중'**으로 바뀌어, 백엔드 동작을 눈으로 확인할 수 있다.

**부수 효과** — 워커 기동 시 모델을 미리 로드(`warm_model`)하도록 바꾸면서 **첫 분석이 느려지는 문제가 사라졌다.**

### 사투리 문제를 푼 방식

방언 데이터를 조사한 결과 **목소리 기준 감정 라벨이 있는 한국어 방언 데이터가 없었다.** 그래서:

- ❌ 방언별 모델 + 앙상블 — 방언별 감정 라벨이 없어 학습 자체가 불가
- ❌ 멜 특징으로 가중치 직접 설계 — "피치 변동 30% 큼"을 "분노 확률 몇 % 감소"로 바꾸는 공식이 없음
- ✅ **모델은 하나, 출력 단계에서 지역별 보정** — 예: 경상 분노 ×0.78 · 중립 ×1.14 후 재정규화, 제주는 데이터가 적어 보정 대신 판단 보류 기준을 0.70→0.75로 상향

이 방식은 "범용 엔진 + 적용 레이어" 설계와 일치하고, 지역이 늘어도 재학습 비용이 들지 않는다.

## 6. 막혔던 지점과 해결 (선별)

| # | 증상 | 원인 | 해결 |
|---|---|---|---|
| 1 | 학습이 매 스텝 깨짐 | WavLM이 학습 모드에서 레이어를 확률적으로 건너뛰어(layerdrop) hidden_states 개수가 달라짐 | `layerdrop = 0.0` + 더미 forward로 개수 실측 |
| 2 | 점수가 너무 잘 나옴 (0.7145) | split이 체크포인트와 어긋나 **데이터 누수** | 출발점 교체, split 지문 검증 |
| 3 | 데이터를 뺐더니 더 나빠짐 | 중립이 줄자 균형 샘플러가 남은 중립을 3배 반복 | 가설 기각, SKT 중립 유지 |
| 4 | 결과 화면에 **이전 분석 잔상** | 데모용 가짜 진행바가 실제 추론보다 먼저 끝나 화면을 넘김 | `LIVE_JOB` 플래그 + "렌더 먼저, 표시 나중" 순서 변경 |
| 5 | 클래스 순서가 뒤바뀔 뻔 | 서버 기본값에 neutral/happy가 반대로 하드코딩 | **체크포인트의 `classes`에서 읽도록** 변경 |
| 6 | 진행바가 63%에서 툭 끊김 | 서버 완료 즉시 화면 전환 | 게이지를 100%까지 채우고 실제 소요·구간 수를 보여준 뒤 전환 |

**교훈 3가지**
1. **연출과 실제를 섞지 마라** — 화면 전환의 주인은 항상 서버 응답이어야 한다
2. **라벨 순서는 모델과 한 쌍** — 코드에 다시 적는 순간 어긋날 준비가 된 것이다
3. **숫자가 좋으면 먼저 의심하라** — 0.7145를 기뻐했다면 누수를 못 찾았다

## 7. 한계

- **성우가 연기한 감정으로 배웠다.** AI-Hub·SKT 둘 다 스튜디오 연기·낭독이라 실제 통화의 흐릿한 말투는 배운 적이 없다

- **조용한 녹음만 들어봤다.** 48kHz 스튜디오 음질. 전화망 8kHz·μ-law·소음은 아직 평가하지 못했다
- **놀람은 test 표본이 98개**로 통계적으로 의미 있는 평가가 어렵다

- 지역 보정 계수는 **아직 실측값이 아니다** (지역별 오탐률 측정 후 교체 예정)

> 세 가지 한계가 전부 **데이터에서 온 것**이라는 점이 중요하다. 모델을 키우는 문제가 아니라 **어떤 목소리를 안 들어봤나**의 문제다.

## 9. 작업 방식 — AI와 어떻게 일했나

16일 · 2명 · 부트캠프 병행. 같은 범위를 AI 없이 했다면 EDA·라벨 검증 2주 + 학습 파이프라인 3주 + 서비스 구현 3주 + 발표자료 2주 ≈ **10주(팀 추정)** 규모였다.

| 사람 | AI | 함께 |
|---|---|---|
| 가설·우선순위·지표 정의·채택/기각 판단 | 분석·학습 스크립트, 발표자료 생성 코드, 문서화 | 이상한 숫자 추적, 에러 해석, 반례 찾기 |

**지킨 규칙 4가지**
1. 숫자는 실측만 — AI가 적은 값도 다시 계산해 확인
2. **AI 제안도 기각한다** — SKT 중립 제외 가설은 AI가 낸 것이었고, 실험 후 수치로 기각했다
3. 이해한 코드만 채택 — 동작을 설명 못 하면 쓰지 않는다
4. 원본 음성은 서버 밖으로 내보내지 않는다

발표자료도 손으로 만들지 않고 **HTML 생성기**로 만들었다(`gen_*.py` → `build.py` → 단일 HTML, 33장). 수치가 바뀌면 다시 생성만 하면 되고, 옮겨 적다 틀릴 일이 없다.
