## 21. 데모 웹 — 랜딩페이지와 화면 흐름 (9/24~9/27)

### 만든 것

- **랜딩페이지**: anime.js 기반. 스크롤에 따라 구성 요소가 하나씩 분해·조립되는 스크롤 연출(sticky pin + rAF 엔진 + 장면별 progress lerp)
- **현장 선택**(상담센터 · 교육 · 돌봄)과 **지역 선택**(수도권 · 경상 · 전라 …)을 랜딩에서 바로 고르고 분석 화면으로 연결
- 화면 4개: 랜딩 → 새 분석(setup) → 분석 중(ana) → 결과(result) / 대시보드(dash)

### 막혔던 것
| 증상 | 원인 | 해결 |
|---|---|---|
| 히어로 영역 내용이 안 보임 | 섹션 높이가 뷰포트보다 작아 진행도 계산이 종료값(투명)으로 고정 | 히어로만 `q = clamp(-rect.top / innerHeight)` 로 별도 계산 |
| 감정 띠가 대각선으로 찌그러짐 | SVG `rect`에 `transform-origin:center`만 주면 SVG 중심 기준으로 변형됨 | `transform-box: fill-box` 추가 |
| 타임라인 선이 중간까지만 그려짐 | `strokeDashoffset` 애니메이션이 중간에 멈춤 | 선 그리기 대신 opacity 페이드로 교체 |
| 선택 구간 표시가 검은 막대로 보임 | anime가 rect의 `opacity:.10`을 1로 덮어씀 | 세 요소를 `<g>`로 묶고 **그룹 단위**로 애니메이션 |

### 스크롤 감각 조정
"너무 딱딱하다" → Lenis 방식의 관성 스크롤(ease 0.10) 도입.
"너무 빨리 지나간다" → wheel 배율 0.78, 장면 전환 lerp 0.22로 낮춤.

## 22. 아키텍처 실제 구현 — FastAPI · Supabase · Docker (9/28)

기획발표에서 그렸던 구조를 **실제로 돌아가게** 만든 날.

### 컨테이너 3개
```
web (nginx)   화면 정적 서빙 + /api 프록시
api (FastAPI) 업로드 접수 · 조회 · 통계 · 서명 URL
worker        같은 이미지, 실행 명령만 다름 — 실제 추론
```
`docker compose up` 한 번에 기동. `--scale worker=N`으로 처리량 확장.

### 비동기 처리 설계
업로드는 **즉시 응답**하고 무거운 추론은 워커가 뒤에서 한다.

- api: 원본을 Storage에 저장 → `analyses` 행을 `status=queued`로 생성 → id 반환
- worker: **2초마다** `claim_next_queued()` 로 한 건 집어감 → 16kHz → 3초 창/1.5초 홉 → WavLM 추론 → 규칙·임계값 적용 → `segments` 저장 후 `done`
- 별도 큐 미들웨어(Redis 등) 없이 **DB 상태 컬럼을 큐로 사용**. 컨테이너가 죽어도 큐에 남아 있어 재시작하면 이어서 처리된다.

### Supabase

- `analyses` / `segments` / `feedback` 3테이블 + Storage(비공개 버킷)
- **RLS 전면 차단**, 서버 전용 secret 키는 `apikey` 헤더로만 전송(브라우저로 나가지 않음)
- 오디오 재생은 **1시간짜리 서명 URL** 307 리다이렉트, 실패 시 서버 릴레이로 폴백

### 모델 연결

- 학습 코드(`ser/`)를 컨테이너에 **읽기 전용**으로 마운트하고 `SERModel`을 그대로 사용
- 서비스 정규화를 학습과 동일하게: `(y − mean) / max|y| × 0.891`
- `prior.json`이 있으면 **로짓 보정(τ=0.6)** 자동 적용
- 실측: **69초 통화 → 45구간 · 추론 36.8초 · 전체 54.6초 (CPU, RTF ≈ 0.53)**

## 23. 이 기간의 버그와 사고 (9/28~9/29)

### 버그 9 — 결과 화면에 이전 분석 잔상 ★ 팀원이 발견
**증상**: 로딩이 끝나고 넘어가면 **이전 데이터 화면이 먼저 뜨고**, 잠시 뒤 내가 올린 파일 결과로 바뀜.
**원인**: 데모용 **가짜 진행바(4.2초)**가 끝나면 자동으로 결과 화면으로 넘어가도록 돼 있었는데, 실제 서버 추론은 그보다 오래 걸린다. 화면은 이미 넘어갔고 데이터는 옛것이 남아 있었던 것.
**해결**

- `window.LIVE_JOB` 플래그 — 실제 분석 중이면 **가짜 진행바가 화면을 넘기지 못하게** 막고, 추론 단계 길이를 90초로 늘리고 상태 문구를 서버 상태로 교체
- `go(name)` 순서를 **"렌더 먼저, 표시 나중"**으로 변경 (빈/옛 화면이 먼저 보이지 않게)
**교훈**: 데모용 연출과 실제 처리 시간이 다르면, **연출이 아니라 서버 응답이 화면 전환의 주인**이어야 한다.

### 버그 10 — 결과 제목의 날짜가 비어 있음
pydantic 응답 모델에 `created_at`이 선언돼 있지 않아 값이 통째로 사라졌다. → `Optional[str]`로 추가.
**교훈**: 응답 스키마에 없는 필드는 **조용히 사라진다**.

### 사고 11 — 클래스 순서 (배포 전에 잡은 큰 건) ★
학습 체크포인트의 클래스 순서는 `angry, sadness, happy, neutral, fear, disgust, surprise`인데, 서버 기본값에 **neutral과 happy가 뒤바뀌어** 있었다. 그대로 나갔으면 **감정 두 개가 서로 뒤집힌 채** 시연될 뻔했다.
→ 하드코딩을 버리고 **체크포인트의 `cfg["label"]["classes"]`에서 읽도록** 변경. `layer_w` 모양도 로드 시 검증.
**교훈**: 라벨 순서는 모델과 한 쌍이다. 코드에 다시 적지 말고 **체크포인트에서 읽는다.**

### 경고 12 — Supabase "Security Definer View"
`daily_stats` 뷰가 생성자 권한으로 돌아 RLS를 우회할 수 있다는 경고.
→ `with (security_invoker = on)`으로 재생성 + `revoke all ... from anon, authenticated`.

### 환경 13 — 포트 충돌과 .env 주석

- `Bind for 0.0.0.0:8000 failed` — 예전 `ser/demo` 스택이 8000을 잡고 있었다 → `API_PORT=8010`
- `.env`의 **인라인 주석이 값의 일부로 읽히는** 문제 → 주석 분리(백업 `.env.bak`)

### 버그 14 — 진행바가 63%에서 툭 끊김 (9/29)
**증상**: 분석이 끝나면 퍼센트가 올라가던 중간에 갑자기 결과 화면으로 넘어감.
**원인**: 서버가 `done`을 주는 즉시 `go('result')`를 호출 — 진행바는 그 자리에서 잘린다.
**해결**: `finishAna()` 추가 — 남은 게이지를 100%까지 채우고(0.5~1.1초), 단계 5개를 0.06초 간격으로 ✓ 처리, 게이지를 초록으로 바꾸며 **"완료 · N초 · M개 구간 분석"** 실제 값 표시 후 0.7초 뒤 전환. 구간 수도 서버 실제 값으로 교체.

## 24. 시스템 상태 모니터링 — "진짜 돌아가는가"를 화면으로 (9/29)

피드백: *"도커가 잘 작동하는지, 모델이 잘 돌아가는지 대시보드에서 확인됐으면 좋겠다."*

### 설계 — DB 마이그레이션 없이 해결
api와 worker는 `./models` 볼륨을 공유한다. 이걸 이용해:

1. **worker가 2초마다 `/models/worker_hb.json`에 심박**을 쓴다 (상태 idle/busy/loading, 처리·실패 건수, 마지막 작업, 모델 로드 여부, 클래스, device)
2. **api가 `/system`에서 그 파일을 읽어** 나이(age)를 계산 — **15초 넘으면 죽은 것**으로 판정
3. 여기에 api 자체 가동시간, Supabase 왕복 지연, 큐 상태(queued/running/done/failed), 체크포인트 존재·크기를 합쳐 한 번에 반환

### 화면
대시보드 맨 위 **5칸**이 5초마다 갱신된다.

| 칸 | 내용 |
|---|---|
| api 컨테이너 | FastAPI 정상 · 가동 시간 |
| worker 컨테이너 | 대기 중 / 분석 중 · **심박 N초 전** · 처리 건수 |
| 모델 | `wavlm-mix40k-tau0.6 로드됨` · CPU · 체크포인트 크기 · 3초 창/1.5초 간격 |
| Supabase | 연결 지연 ms · 3테이블 |
| 작업 큐 | 대기 · 분석 중 · 완료 · 실패 |

워커가 내려가면 즉시 빨간 줄, 큐가 밀리면 노란 줄. **파일을 올리면 worker 칸이 '대기 중' → '분석 중'으로 바뀌는 것**이 백엔드 동작의 가장 직접적인 증거가 된다.

### 덤 — 모델 예열
워커 기동 시 체크포인트를 **미리 메모리에 올리도록**(`warm_model`) 변경.

- 대시보드에 "로드됨"을 정직하게 표시할 수 있고
- **첫 분석이 느려지는 문제가 사라졌다** (시연에서 가장 불안했던 지점)

## 25. 발표덱 최종화와 피드백 반영 (9/29)

### 받은 피드백 4가지와 조치
| 피드백 | 조치 |
|---|---|
| 소제목이 너무 추상적이다 | 18개 제목을 숫자·동작이 드러나게 교체 (예: "라벨부터 의심했다" → **"지시한 감정과 사람이 느낀 감정이 68.1%만 일치"**) |
| 과정이 안 보인다 — 텐서보드 기록이 있어야 | **텐서보드 장 신설**. 실제 event 파일에서 읽은 값으로 ① 과적합 시작 지점 ② 레이어 가중치 쏠림 ③ 임계값 14단계 곡선 |
| 모델 선정 수치가 눈에 안 들어온다 | 표 → **막대 + 큰 숫자 + 채택/기각 배지**로 재구성. 1등(앙상블 0.745)을 회색 '기각'으로 대비 |
| 아키텍처는 대시보드 구조까지 있는 버전으로 | 기획발표 기반 상세본으로 교체하되 **실제와 어긋난 부분 정정**(Redis→DB 큐, JWT→RLS, Realtime→폴링, RTF 0.057→0.53) |

### 추가 정리

- **비정형 데이터(음성 파형)**임을 명시하고, 원천 '상황' 라벨 폐기 → 5명 투표 재라벨링 과정을 파이프라인 장에 표기
- 모든 수치에 **지표명 + 시험지(n) + 조건**을 붙임 (예: `test UAR · 전체 test n=4,840 · τ0.6 보정 후`)
- "들린 감정" → **"사람이 느낀 감정"**으로 용어 통일
- "진행 경과" → **"간트 차트"**
- AI 협업 장에 **기간 단축** 추가: 16일 vs 팀 추정 10주, 실측(실험 10회 · 코드 5,120줄 · 문서 6종 · 발표 33장)

### 발표덱 기술 메모
슬라이드는 손으로 만들지 않고 **HTML 생성기**로 만든다.
`gen_*.py` → 슬라이드 조각 → `build.py`(순서·제목·가독성 보정) → `assemble.py` → 단일 HTML.
슬라이드별 전용 애니메이션은 `template.html`의 **FX 레지스트리(슬라이드 id → 함수)**에 등록. 수치가 바뀌면 다시 생성만 하면 되고, 옮겨 적다 틀릴 일이 없다.

## 26. 이 기간의 교훈 5가지

1. **연출과 실제를 섞지 마라** — 가짜 진행바가 실제 처리보다 빨리 끝나면 사용자는 "고장 났다"고 느낀다. 화면 전환의 주인은 항상 서버 응답.
2. **라벨 순서는 모델과 한 쌍** — 코드에 다시 적는 순간 어긋날 준비가 된 것이다.
3. **모니터링은 기능이 아니라 신뢰** — "돌아간다"는 말보다 심박 0.9초 전이라는 숫자 하나가 강하다.
4. **DB 상태 컬럼도 훌륭한 큐** — 새 미들웨어를 붙이기 전에 있는 걸로 되는지 먼저 본다.
5. **발표자료도 코드로** — 숫자가 바뀔 때마다 33장을 손으로 고치는 대신 다시 생성한다.
